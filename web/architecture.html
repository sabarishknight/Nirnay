Human in the loop
  • Applicant consent before bureau and AA pulls.
  • Credit officer edits the note and decides; an override needs a reason.
  • Deviations go to the authority in the delegation of powers.
  • Declines need a person and written reasons.
  • Advocate, valuer and RCU stay human.
Feedback loop
  • Decisions and override reasons stored in officer_decisions (Firestore and BigQuery in production).
  • Lending head reviews override patterns monthly.
  • Fixes ship as policy-pack or prompt changes through CI/CD, tested on an evaluation set of past files.
Governance
  • Every agent step logged with source and clause.
  • Data stays in India: BigQuery and Cloud Run in Mumbai.
  • Least-privilege service account; VPC Service Controls and CMEK in production.
  • Aadhaar masked at source; Sensitive Data Protection on documents.
  • DPDP Act consent records; RBI IT outsourcing and model-risk governance.
One review, end to endWhat happens when the officer clicks Run agent review
  1. The browser calls POST /api/run/{file}; the runner starts a session and streams events back over /events.
  2. Seven parameterised queries read the file from BigQuery: application, property with valuation and legal reports, relationship, repayments, bank income, the gold features row, co-applicant.
  3. Each PDF goes to Gemini with the list of fields to return as JSON; reads run in parallel. The agent compares payslip, Form 16, bank credits, ITR and GST.
  4. PAN/CKYC, CIBIL, CERSAI, Account Aggregator and EPFO or GST are called at once; responses are written to lending_raw.ext_api_log.
  5. Policy rules run in code with parameters from the policy pack; each result carries a clause id and its sources.
  6. The routing rule picks the recommendation and the sanctioning authority; for deviations it computes the loan, tenor or co-borrower change that fits policy.
  7. Gemini drafts the note from the verified facts only, citing clauses. The file goes to the officer; their decision is written to lending_gold.officer_decisions.
